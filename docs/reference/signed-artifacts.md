# Signed artifacts: two mechanisms, one question

A desktop update and a mobile pack are both a signed thing that gets installed. They answer the same
five questions in two vocabularies. This document names the correspondence, the differences that
matter, and the shape that lets either describe itself the same way.

Written for the Suite Go phase, where packs are the primary architecture. Nothing here asks Go to
change its format.

## The five questions

| Question | Desktop app | Mobile pack |
|---|---|---|
| What is it? | `suite.app` manifest: id, version, capabilities | `manifest.json`: id, name, version, entry |
| Is it intact? | The feed names one AppImage with its hash | Per-file sha256 for every file in the pack |
| Who signed it? | ed25519, detached `.sig` beside `latest-linux.yml` | ed25519 over the manifest, `signature` field |
| Which key do we trust? | Pinned in `@suite/desktop`: `SUITE_UPDATE_PUBLIC_KEY`, first 32 hex of sha256 as the fingerprint | Pinned in the APK |
| What if it fails? | Install refused; the working copy stays | Install refused; the installed version stays |

## Where they genuinely differ

**A feed of versions versus a bundle.** Ours is `latest-linux.yml`, generated by electron-builder,
naming **one** artifact per channel; the hub reads the feed and decides. Theirs is one manifest for
one pack; the store lists, installs and uninstalls. Neither is a superset of the other, and a shared
schema must not pretend otherwise.

**One hash versus many.** An AppImage is one file, so the feed's hash covers everything. A pack is
many files, so each needs its own hash — otherwise an attacker swaps one asset inside a valid
signature.

**Where the entry point lives.** Deliberately opposite. `suite.app` carries **no** executable path,
because a manifest that names the binary lets a tampered one point the launcher anywhere; the
install location belongs to Start's own registry. A pack **must** name an entry module, because the
host imports it rather than spawning it.

**Who provides the runtime.** An app ships Chromium. A pack runs inside the host's, which is why a
pack needs `minimumHostVersion` and an app does not.

## The shape both can use

`@suite/contracts` now exports `suiteArtifactSchema` — format `suite.artifact`. It is **additive and
currently unused**: nothing writes it, nothing reads it, and no installer has been changed.

```json
{
  "format": "suite.artifact",
  "contractVersion": "1.0.0",
  "kind": "app | pack",
  "id": "canvas",
  "name": "Suite Canvas",
  "version": "0.1.8",
  "minimumHostVersion": "0.4.0",
  "entry": "index.js",
  "files": [{ "path": "...", "sha256": "…64 hex…", "size": 142671251 }],
  "signature": { "algorithm": "ed25519", "keyFingerprint": "…32 hex…", "value": "…base64…" }
}
```

The schema enforces the four rules both mechanisms already keep, and refuses the combinations that
would be a vulnerability:

- `entry` is **forbidden** for `kind: "app"` and **required** for `kind: "pack"`.
- A file path is relative and cannot climb out of the artifact (`../`, absolute paths).
- Two files cannot share a path.
- Unknown fields are rejected, so a future field is a visible mismatch rather than a silent omission.

## What this does not solve, and does not claim to

**Canonical bytes.** The signature covers "the canonical bytes of this document with the signature
removed". Defining that precisely — key order, whitespace, number formatting — is the part that
breaks in practice. Both sides currently sign bytes they generated themselves, which works because
each verifier is the same code as its signer. A shared format that two implementations must agree on
needs that definition written down before either side signs anything new, and this document does not
attempt it.

**Channel semantics.** Ours has stable/beta/alpha; theirs has no channel concept. Left out of the
schema rather than guessed.

**Revocation.** Neither mechanism has a way to say "this artifact is now bad". Out of scope for both
today, and worth saying so plainly.

## Recommendation

Do not converge the formats. Converge the **vocabulary**:

1. Keep electron-builder's feed for desktop. Keep the pack manifest for mobile.
2. When either side needs to describe an artifact to the other — a download page, a diagnostic, a
   future shared store — emit `suite.artifact`.
3. If a shared installer ever arrives, write the canonical-bytes definition **first**, then the
   verifier, then the signer.

Step 1 is what ships today. Step 2 costs nothing until it is needed. Step 3 is the one that would
hurt if done last.
